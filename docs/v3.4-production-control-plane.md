# AutoDoc v3.4 — Production Control Plane

This branch extends the v3.4 production snapshot work with a deterministic control-plane layer for release reproducibility.

## 1. Production snapshot lifecycle

A production snapshot is an immutable selection record for the exact visual lineage used at render time.

```text
Scene
  -> selected Visual Entity
      -> current Visual Version
          -> source Asset
              -> Asset License
          -> source Generation Attempt (nullable for upload/stock/url)
```

The persisted snapshot stores, per scene:

- `scene_id`
- `scene_visual_id`
- `scene_visual_version_id`
- `source_generation_attempt_id`
- `source_asset_id`

The snapshot also stores a SHA-256 `snapshot_hash` and a lifecycle `status`.

## 2. Snapshot gate

A snapshot can only be created when every current scene has:

1. exactly one selected visual entity;
2. an approved current visual version;
3. a visual version sourced from the current scene version;
4. a concrete `source_asset_id`;
5. a verified asset license;
6. a retrievable `object_key`.

This is deliberately stricter than merely checking the visual approval state.

## 3. Verification

`verifyPersistedProductionSnapshot(projectId, snapshotId)` performs two independent checks:

- **integrity check:** the persisted selection list still hashes to the stored snapshot hash;
- **current-state check:** the current project selection still resolves to the same snapshot hash and passes the production gate.

A snapshot becomes `drifted` when the project has moved on, for example after a new visual version becomes current or a scene version changes.

Snapshots are not silently rewritten when drift occurs.

## 4. Deterministic production manifest

`server/production-manifest.js` turns a persisted snapshot into a complete release manifest containing:

- project identity and release context;
- snapshot identity and hash;
- visual entity/version lineage;
- scene-version reference;
- exact asset reference and storage metadata;
- checksum and media dimensions where available;
- license state and licensing metadata;
- generation attempt/provider/model/parameters when the asset came from a generation attempt;
- provider request ID, timing and cost metadata for generation attempts.

The manifest receives its own SHA-256 `manifest_hash`.

This creates two useful identities:

```text
snapshot_hash  = identity of the exact production selection
manifest_hash  = identity of the expanded reproducibility manifest
```

## 5. Verification contract

`verifyProductionManifest(projectId, snapshotId, expectedManifestHash)` returns:

```json
{
  "ok": true,
  "snapshot": {
    "status": "valid"
  },
  "manifest_hash": "<sha256>",
  "expected_manifest_hash": "<sha256>",
  "hash_matches": true
}
```

A caller can therefore verify both project drift and an externally stored manifest hash before starting a release/render operation.

## 6. Test coverage

The v3.4 tests cover:

- missing visual selection;
- exact snapshot persistence;
- snapshot hash generation;
- project-scoped snapshot listing;
- unchanged snapshot verification;
- drift after a new visual version;
- stale selected visuals after a scene update;
- complete manifest lineage;
- manifest hash verification;
- tampered expected manifest hash rejection.

The control-plane code is intentionally kept separate from the HTTP routing layer so the same verification primitives can later be called by the render worker, CLI, or API without duplicating gate logic.
