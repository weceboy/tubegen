# AutoDoc v3.7 — Persisted Render Attestation Verification

v3.7 extends v3.6 from write-time integrity to post-persistence verification.

## Purpose

A completed production render is not trusted forever merely because it passed the v3.6 completion gate. Downstream publication, export, archival and recovery flows can independently verify the persisted job and asset metadata.

## Verification contract

`verifyPersistedRenderOutput(project_id, job_id)`:

1. Requires the render job to exist in the requested project.
2. Requires the job to be `completed` and to reference exactly one output asset.
3. Resolves the output asset through the same project boundary.
4. Requires a SHA-256 asset checksum.
5. Requires the stored object key to remain under `renders/<project_id>/`.
6. Requires a video MIME type.
7. Recomputes the output manifest hash from persisted asset metadata and the stored lineage hash.
8. Requires the job checksum and asset checksum to match.
9. Returns a structured failure instead of throwing for detected integrity drift.

This creates a reusable fail-closed verification primitive for future publish/export gates.

## Tamper model

The verifier detects metadata tampering even when the database row itself remains present. For example, changing the persisted output object key invalidates the manifest attestation and therefore blocks downstream trust.

The verifier does not claim to hash remote object bytes. Byte-level verification remains the responsibility of the storage adapter; the persisted checksum is the authoritative content identity recorded by the renderer/storage boundary.

## v3.7 acceptance criteria

- A completed render verifies successfully immediately after completion.
- Changing persisted output metadata causes verification to fail.
- Cross-project output assets are rejected.
- Non-video output remains rejected.
- Invalid or missing SHA-256 checksums remain fail-closed.
