# AutoDoc v3.3 — Definition of Done

This document turns the v3.3 developer briefing into an implementation checklist. It is intentionally stricter than the current regression suite: green tests are necessary, but not sufficient.

## Visual data model

- [x] `scene_visuals` is the stable candidate-line entity.
- [x] `scene_visual_versions` is the evolving creative version.
- [x] `generation_attempts` is the provider-call level.
- [x] `scene_assets` is the visual file/provenance level.
- [x] `scene_visual_versions.source_asset_id` resolves to `scene_assets`.
- [x] `generation_attempts.result_asset_id` resolves to one asset on successful generation.
- [x] `asset_licenses.asset_id` attaches licensing to the asset.
- [x] upload/stock/URL assets can exist without a generation attempt.

## Entity / version / attempt rules

- [x] Same prompt + same scene version => new generation attempt.
- [x] Prompt change => new version on the same visual entity.
- [x] Scene-version change => new version on the same visual entity.
- [x] Explicit independent candidate line => separate visual entity.

## Selection vs artifact state

- [x] `selection_state` exists only on `scene_visuals`.
- [x] Artifact `status` remains on `scene_visual_versions`.
- [x] Selection and approval are independent.
- [x] Snapshot selection is tied to the selected entity's current version.

## Risk override

- [x] `risk_override` is not an approval mode.
- [x] Override clears the block but does not approve the artifact.
- [x] Approval after an override requires `human`.
- [x] Approval after an override links `linked_risk_override_id`.
- [x] Override and approval are separately audited.

## Research change classification

- [x] Classification is stored as `system_suggested_change_type`.
- [x] Final `change_type` defaults to the system suggestion.
- [x] Content -> metadata downgrade requires a reason.
- [x] Downgrade is audited.
- [x] Mixed cannot be downgraded to metadata.
- [x] Metadata -> content is allowed without justification.
- [ ] Adding/removing a non-duplicate source must be classified as `content`.
- [x] Adding/removing an actually duplicated source is treated as metadata.
- [x] Source title/publisher/tags/internal-notes changes are metadata.
- [x] Unlisted source fields conservatively classify as content.

## Production reproducibility

- [x] Production snapshots contain visual entity id.
- [x] Production snapshots contain visual version id.
- [x] Production snapshots contain generation attempt id where applicable.
- [x] Production snapshots contain concrete asset id.
- [x] Asset licensing is resolved from the selected version's `source_asset_id`.

## Risk policy inheritance

- [x] Project/channel/global precedence exists.
- [x] Policy fields can fall back independently.

## Remaining implementation item

The one known specification gap is source presence classification: a newly added or removed source is content unless the change is only the addition/removal of an in-content duplicate. The existing regression test suite covers duplicate-source behavior but does not yet protect the general add/remove rule.

Before calling v3.3 complete, add an executable acceptance test for both a unique source addition and a unique source removal, and make both resolve to `content` with downstream invalidation.
